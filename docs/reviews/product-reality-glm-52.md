# Product Reality Review — GLM-5.2

## Verdict
- Overall score: 4/10
- Product state: feature checklist
- One-sentence diagnosis: Grounded Route ships a faithful, auditable WebMCP workspace but never collapses its evidence board into the one answer a time-pressed resident actually needs, so the human is forced to operate a research dashboard instead of receiving a decision.

## Ranked high-impact findings

1. **Profiles are cosmetic — severity: critical.** Selecting "Wheelchair user" vs "School-pickup parent" changes only a one-line banner (`App.tsx:131-135`). `demo_scenarios.json.defaultSegmentIds` and the displayed `scenarioMappings` are profile-independent; the profile-specific segments that exist in the fixture (`seg-wheelchair-alternate`, `seg-parent-stroller-route`, `seg-cyclist-bypass-west`) are never routed into the default route or the stage list. User consequence: the persona the product hinges on ("wheelchair-using parent") produces no personalized outcome, so the central demo promise is broken. Direction: make profile selection the routing input — `selectProfile` should swap `activeSegmentIds` to the profile-relevant segment set and filter `scenarioMappings` to mappings whose `segmentIds` intersect that set, so the map and evidence literally change per persona.

2. **No decision answer, only evidence ingredients — severity: critical.** The product surfaces raw segments, mappings, and source references but never computes the resident's question ("does this affect my school pickup?"). `map-01` covers all 10 default segments, so "Stage" paints the whole corridor blue and the resident must read two paragraphs of rationale to infer impact. User consequence: a parent with minutes gets a dashboard to research, not an answer. Direction: introduce a single "Impact verdict" line per staged mapping computed from `mapping.segmentIds ∩ activeSegmentIds` and the profile's `constraints` (e.g., "Affects you: the Saloma Link bridge segment has `steps`; your wheelchair profile needs step-free — alternate route available via `seg-wheelchair-alternate`"), placed above the map, not buried in the evidence board.

3. **"Stage" is undiscoverable and meaningless as labelled — severity: high.** The verb appears only as a small `Stage` button beside a monospace ID (`map-01`) inside segment cards (`RouteSegmentList.tsx`). It has no object, no tooltip, no explanation of what staging does or why a resident would do it; `docs/TECHNICAL_DESIGN.md` calls it "stage an impact overlay" but the UI never says so. User consequence: the pivotal interaction of the demo is opaque; residents click it blindly or skip it. Direction: rename to a resident-facing action with a stated outcome ("Show how this plan changes my route") and surface a one-line "what staging does" affordance the first time a mapping appears.

4. **First screen fails the value-proposition test — severity: high.** The `h1` is the scenario's internal title, the only CTA is "Load illustrative demo", and the README's resident-facing tagline is absent from the page (`App.tsx:107-112`, `index.html`). User consequence: a first-time visitor cannot tell within seconds whether the tool is for them, so they bounce before reaching any value. Direction: replace the demo title with a resident value heading ("Will the KL 2040 plan change the route you walk?") and make the primary CTA copy state the outcome ("See how the Saloma Link plan affects your route").

5. **Cognitive load / vertical sprawl buries the answer — severity: high.** The loaded workspace stacks map + 14 segment cards + 9 evidence cards + draft form + audit log in one 7047px (mobile 8845px) column (`journey.json`, `App.tsx:118-145`). The audit trail, `revision`/`audit events` counts, and `> source-reference`/`> curated-interpretation` badges are reviewer vocabulary, not resident vocabulary. User consequence: the decision-relevant signal is a small fraction of the scroll; the rest reads as an internal QA report. Direction: collapse the default view to a verdict + map + "affected segments" shortlist, and move full source references, uncertainty, and the audit trail behind a "Show the evidence" disclosure.

## WebMCP verdict
**Helpful but incidental** — for the human flow actually exercised here. The six registered tools (`get_route_context`, `find_plan_evidence`, `stage_impact_overlay`, `clear_staged_overlay`, `draft_public_comment`, `get_review_status` in `src/webmcp/adapter.ts`) and the `WorkspaceBridge` genuinely let an agent read and mutate the *same* shared state the resident sees, which a plain chatbot cannot do — so the architecture earns its keep *in principle*. But the recorded journey (`journey.json`) is human-only: there is no agent surface in the UI, no agent turn in the flow, and no resident-visible difference when WebMCP is present. The agent can stage and draft, yet the resident still has to read the same evidence board and type the same draft fields by hand. WebMCP becomes essential only once an agent actually drives the verdict-and-draft loop on screen; until then it is a latent capability the product never shows the user.

## One redesign bet
**Revised thesis:** Grounded Route should be a 30-second *verdict machine* for one resident and one corridor, not an evidence workspace — "Does this plan change the route you walk, yes or no, and here is the one thing to say about it."

**Main demo moment:** a wheelchair-using parent picks "school pickup", sees one map with their route, one line "Yes — the Saloma Link bridge segment has steps and the 2040 plan does not yet commit to an elevator retrofit; a step-free alternate exists," and one pre-drafted, source-linked comment they can edit and export.

**3-step product redesign sequence:**
1. Make profile the routing input: `selectProfile` swaps `activeSegmentIds` to the profile-relevant segments and filters `scenarioMappings` accordingly, so the map and evidence re-render per persona (fixes finding 1 and 2 in one move).
2. Add an "Impact verdict" computed from `mapping.segmentIds ∩ activeSegmentIds` plus the profile's `constraints`, rendered as a single headline+next-action above the map; demote full source references, uncertainty text, and the audit trail behind a "Show the evidence" disclosure.
3. Auto-generate the draft from the staged mapping + verdict (prefilled `userPosition`/`requestedChange` from profile + affected segments, with source links already attached), so the resident edits rather than authors — then keep the existing human-only approve/export gate.

## Preserve / demote
- Preserve: the human-only approve/export gate and revision invalidation model (`AuditConsentStrip.tsx`, `actions.ts` `approveDraft`/`residentRequestExport`) — it is the correct safety spine.
- Preserve: the evidence-integrity vocabulary (`> source-reference` vs `> curated-interpretation`, `certaintyLevel`, `uncertainty`, `boundaryNote`) — it is the product's credibility moat and should survive any redesign, just relocated.
- Preserve: the shared-state `WorkspaceBridge` + six WebMCP tools as the agent channel — it is the only credible path to the "agent drives, resident approves" loop that would make WebMCP essential.
- Demote/remove: the full `Audit trail` / `Revision` / `Audit events` UI exposed to the resident (`AuditConsentStrip.tsx` audit log) — engineering hygiene, not a user need; keep it in the export payload, not on the page.
- Demote/remove: the 14-card undifferentiated `RouteSegmentList` default view (`RouteSegmentList.tsx`) — replace with an "affected segments" shortlist driven by the verdict; the full list belongs behind a disclosure.
- Demote/remove: the standalone `Open draft panel` gate and the empty draft form (`DraftReviewPanel.tsx` closed state) — the draft should open pre-filled from the verdict, not wait behind a button for the resident to author from scratch.
